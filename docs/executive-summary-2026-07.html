01 Propósito del sistema

FitNotes App es una aplicación de seguimiento de entrenamiento de fuerza y fitness (workout logging), construida como réplica funcional y visual completa de la app de referencia FitNotes, con dos clientes propios — web y mobile — que comparten la misma lógica de negocio.

Resuelve el problema de registrar entrenamientos (ejercicios, series, repeticiones, peso, distancia o tiempo según el tipo de ejercicio), ver progreso histórico (récords personales, 1RM estimado, gráficas), planificar rutinas reutilizables, hacer seguimiento corporal y fijar objetivos — con los cálculos deportivos estándar del dominio (fórmula de Brzycki para 1RM, cálculo de discos de barra, ritmo y velocidad en cardio).

Su rasgo más distintivo: el cliente mobile funciona por completo sin cuenta desde el primer arranque (modo invitado local). Crear o vincular una cuenta activa la sincronización en la nube, pero nunca es una barrera de entrada.

Patrón central: repositorio espejado

Cada entidad (workouts, exercises, routines, body-tracker, goals, progress) tiene un repositorio remoto (createXxxRepository(supabaseClient)) y, en mobile, un repositorio local SQLite con el mismo nombre de método y la misma forma de respuesta ({data, error}). La UI de mobile habla siempre con SQLite local, sin saber si hay red o cuenta.

Capa offline de mobile

La pieza arquitectónica más compleja del proyecto:

SQLite local
Espeja 13 tablas remotas. UUIDs reales generados en cliente (nunca IDs temporales), tombstones para deletes (evita "resucitar" filas borradas en un pull concurrente), cascadas de FK replicadas a mano.
SyncEngine
Cola de operaciones pendientes durable en SQLite, resolución de conflictos (gana lo local si está "sucio", si no gana el más reciente por updated_at), disparadores al volver a primer plano o reconectar red.
Identidad invitado
local_identity resuelve siempre un userId de escritura, con o sin cuenta. Al vincular cuenta real, un "claim" reescribe ese user_id en las 13 tablas y en las operaciones ya encoladas, en una sola transacción.
PRs offline
Los récords personales se calculan en JavaScript replicando el trigger SQL remoto, para que el modo invitado también genere trofeos sin depender de red.

04 Flujos de datos más importantes

Registrar un set (mobile, offline)

UI → repo local SQLite (insert, UUID real, transacción) → cola de operación pendiente → cálculo de PR en la misma transacción → push al reconectar (orden respetando FKs)

Sincronización cross-device

Foreground / reconexión → pull paginado por marca de agua (updated_at) → aplica filas remotas (reglas de conflicto) → notifica tablas cambiadas → pantallas releen desde SQLite

Registrar un set (web)

UI → Supabase directo (RLS por auth.uid()) → trigger SQL recalcula el récord personal

Vincular cuenta desde modo invitado

Login/registro → detecta user_id de sesión ≠ invitado local → reescribe user_id en tablas + pendientes → sync() normal = bootstrap completo (watermarks vacíos ⇒ pull total)

Backup y CSV

Configuración → backupRepository (exportar / restaurar) → solo disponible con cuenta real, no en modo invitado

05 Integraciones con sistemas externos

Supabase activo

Postgres con Row Level Security por usuario, Auth (email/password), funciones RPC (delete_user()), triggers SQL para récords personales.

Google Drive API activo

Backup automático desde web (auth / callback / backup / disconnect). Rotación automática, conserva las 5 copias más recientes.

Vercel activo

Hosting y despliegue del cliente web, con headers de seguridad (CSP) duplicados en vercel.json.

06 Estado actual

Ambos clientes tienen paridad funcional y visual completa frente a la app de referencia. El plan de arquitectura offline-first en mobile (6 fases) está terminado y verificado en dispositivo físico.

Limitaciones aceptadas (no bloqueantes)

  • PRs duplicados tras claim+sync — un récord generado offline y el mismo regenerado por el trigger SQL remoto al pushear pueden convivir como dos filas distintas.
  • Sesión no sobrevive a force-stop (Android) — pese a persistencia configurada, forzar el cierre del proceso deja el sync detenido en silencio hasta iniciar sesión de nuevo manualmente.
  • Multi-dispositivo en modo invitado — el mismo usuario como invitado en dos dispositivos antes de crear cuenta genera filas duplicadas al vincularse a la misma cuenta.
